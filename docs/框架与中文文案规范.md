# Averie Skin v3 分析框架与中文文案规范

2026-09-16。基于交接包对应的 5d0fde8 版本改写。以本次用户反馈为准，将需求包作为产品背景和验收依据；不是照搬其中供其他 AI 使用的指令。实际源码、模型合同、展示合同、规则和示例一并交付。

## 1. 用户打开结果后要得到的答案

先回答：我的皮肤看起来怎么样？哪里值得留意？今天该怎么护理？哪些产品需要、哪些可以不加？

免费结果依次展示本次引擎、肤质外观倾向、外观评分、具体优势、最多两个关注点、七项观察。完整报告包含总览、七项说明、部位提示、十四天早晚安排、六类产品取舍、使用注意，默认只展开总览。

评分是统一呈现外观观察的产品规则，不是仪器测量、健康评级、皮肤年龄或模型置信度。普通自拍不能测含水量、皮脂分泌率、屏障功能、胶原含量，也不能确认敏感肌或疾病。

## 2. 调研如何落实到这次改版

这里研究的是可公开查看的官方说明、演示页面和社区原帖；没有声称完成竞品登录后的真实自拍测试。社区样本用于观察自然表达，不作为护肤建议的医学依据，也不是用户调研的统计样本。

| 参考 | 可观察到的做法 | 本次采用的做法 |
|---|---|---|
| [Skin Bliss 官方](https://getskinbliss.com/) 与 [FAQ](https://getskinbliss.com/blog/skin-bliss-app-faq/) | 将皮肤关注点、日常护理与产品信息连接起来 | 观察、护理取舍、产品卡之间有可追溯字段；产品必须解释为什么出现在这份报告中 |
| [Perfect / YouCam 官方演示](https://www.perfectcorp.com/business/showcase/skincare/hd-diagnostics) | 按毛孔、细纹、泛红等用户能辨认的项目呈现结果 | 采用直接的中文项目名；不显示内部 key、缩写或“线→细纹”映射 |
| [Cetaphil Skin Analysis](https://www.cetaphil.com/us/skin-analysis.html) 与 [官方说明](https://www.cetaphil.com/us/skincare-tips/skincare-science/how-ai-skin-analysis-can-benefit-your-skin.html) | 从分析结果引导到护理方案 | 完整报告围绕早晚步骤与产品取舍组织，避免只有分数和科普 |
| [虎扑用户原帖，2023 年](https://m.hupu.com/bbs/58161789.html) | 用户用“T区出油、两颊有点干”表达状态，并关心乳液、面霜、精华要不要都用 | 采用“部位＋看得见的表现”，明确乳液与面霜的替代关系 |
| [豆瓣用户讨论，2013 年](https://www.douban.com/group/topic/39822339/) | 使用“两颊干”“洗完有点干”等具体体感表达 | 增加可选的洗后紧绷、近期刺痛发痒问题，不让照片代替用户体感 |

上述社区帖具有时间局限，只用于语言参考。本次未取得可核验的小红书登录内原帖，不把搜索摘要或营销文章包装成小红书用户研究。也没有采用社区回复中的治疗建议。

竞品的诊断性说法、准确率营销、购物跳转不移植到 Averie。基础护理的简化原则参考 [AAD 简单护理建议](https://www.aad.org/public/everyday-care/skin-care-basics/care/skin-care-budget)，新品观察参考 [AAD 新品小范围试用](https://www.aad.org/public/everyday-care/skin-care-secrets/prevent-skin-problems/test-skin-care-products)。十四天是安排，不是见效期限。

## 3. 输出架构

一次分析经过以下顺序：

1. 输入照片、年龄、性别；可选填写最多两个关注目标、洗后是否紧绷、近期使用产品是否刺痛发痒。未知保留 unknown，不视为“没有”。
2. 视觉模型只生成照片观察，遵守 `llm-output.schema.json`。不生成总分、品牌、配方、购买建议。
3. `reportValidation.ts` 检查结构、长度、七项齐全、观察区域、图片可用性、禁止表述和部分分数矛盾。失败则返回重试提示，不补随机分数，不回退为示例。
4. `mapLlmToResult.ts` 由固定规则计算表现分、总分、状态、关注顺序；不因年龄或性别加减分。
5. `carePlan.ts` 综合本次观察与用户体感，逐项生成六类产品决策与早晚步骤。
6. `productCatalog.ts` 提供已经核对地区、型号、成分和资料来源的候选；模型不能自行发明产品。
7. 页面使用同一份 `AnalysisResult` 展示；`report-output.schema.json` 是完整应用对象的合同。

两个 Schema 都是 JSON Schema Draft 2020-12。运行 `npm test` 会编译并核验两份合同，`npm run export:contracts` 从源码导出合同、提示词、产品库和完整示例，避免人工复制后漂移。模型侧运行时校验器只实现本项目使用的 Schema 关键字，不宣称是通用 JSON Schema 引擎。

### 关键字段

| 字段 | 生成者与用途 |
|---|---|
| `version / schema_version` | 固定 3.0，拒绝旧格式直接混入 |
| `quality` | 模型给出 usable / limited / unusable，必须与可判断项目数量一致 |
| `perception[key].severity` | 可见关注程度 0–4；看不清为 null |
| `observation` | 本次具体观察，不得被前端静态文案覆盖 |
| `detail` | 解释观察与护理取舍，不套固定科普段落 |
| `action` | 一个现在能执行的动作 |
| `regions` | 照片实际支持的部位；不为凑布局生成部位 |
| `analysis_status` | 应用计算 complete / partial / insufficient |
| `skin_score.value` | 完整七项时计算；否则为 null，不折算剩余项目 |
| `summary_free.priorities` | 最多两个 key，不强制凑两个问题 |
| `products_paid.decisions` | 六类必须各出现一次，含是否需要、理由、对应分项、候选和缺货/资料不足说明 |
| `candidates[].ingredients` | 2–4 个核对过的成分与角色 |
| `candidates[].mapped_concerns` | 对应本次观察的 key，不等于宣称这些观察都是问题 |
| `candidates[].reasons` | 3–5 句，说明护理需求、成分或剂型选择、使用位置与取舍 |
| `source_url / checked_on` | 内部资料追溯；界面不显示外链、不提供购买按钮 |

### 七项命名与观察范围

| key | 显示名 | 观察边界 |
|---|---|---|
| radiance | 暗沉 | 局部发暗与整体明亮感，不评价肤色深浅；光线干扰时不判断 |
| oiliness | 出油 | 照片中的油光分布，不测皮脂分泌率 |
| pores | 毛孔 | 轮廓明显程度，不把毛孔直接叫作堵塞或黑头 |
| texture | 粗糙起皮 | 表面不平整、起皮；不重复计算毛孔和细纹 |
| tone_evenness | 肤色不均 | 可见色差；泛红另列，不重复扣分 |
| fine_lines | 细纹 | 可见线条；不能推断胶原流失 |
| redness | 泛红 | 发红的位置与范围；不能确诊过敏或其他疾病 |

“干燥”“刺痛”可以来自用户自述，来源必须说清楚。不得把无反光直接叫作干皮，把泛红直接叫作敏感肌。

## 4. 评分和差异规则

| 模型 severity | 可见程度 | 应用表现分 | 状态 |
|---:|---|---:|---|
| 0 | 清晰画面中不突出 | 100 | 表现不错 |
| 1 | 轻微、局部 | 85 | 表现不错 |
| 2 | 局部清楚可见 | 70 | 可以留意 |
| 3 | 一个主要区域明显 | 50 | 优先关注 |
| 4 | 多个主要区域明显 | 25 | 优先关注 |
| null | 无法判断 | 不显示数值 | 暂无法判断 |

锚点是 MVP 的展示约定，尚未用标准化标注集校准，不暗示这些分数具有测量精度。UI 的分项状态阈值为 80–100、60–79、0–59。总分是完整七项表现分的算术平均值四舍五入；示例 `(85+50+50+70+85+100+70)/7 = 73`。

总分标签：0–39“先做基础护理”，40–59“需要多些关注”，60–79“局部值得留意”，80–89“整体表现不错”，90–100“整体比较均衡”。总分不掩盖单项优先关注。

关注点先选低于 80 分的项目。优先关注级别排在前面，再在同一关注级别内参考用户目标，之后按表现分由低到高。最多两个；全都表现不错时不给用户制造问题。好、中、需关注分别落在“保持”“局部调整”“优先处理这一护理取舍”，而不是同一句夸赞换形容词。

## 5. 中文文案规则

一句话讲清一个意思，用句号、逗号和必要的顿号；不用中点、箭头和斜杠串标签。专业程度来自具体部位、观察依据和合理取舍，不来自生造短语。

| 位置 | 写法 | 建议长度；程序硬限制 |
|---|---|---|
| 倾向 | 短标签；随后解释分区差异及边界 | 标签 4–8 字；说明 12–100 字 |
| 总览 | 一个具体优势＋一至两个关注点 | 约 40–90 字；不能凭空加优势 |
| 短评 | 部位＋可见表现＋程度 | 约 12–30 字；8–60 字 |
| 分项说明 | 这次看见什么＋对护理的影响＋少做/先做什么 | 通常 50–100 字；30–180 字，不为达字数重复 |
| 动作 | 一个行为＋必要的部位/条件 | 约 12–35 字；8–90 字 |
| 产品理由 | 本次需要什么＋此配方/剂型为何可选＋怎么放入已有步骤 | 3–5 句，不复述广告 |

原需求包提到每项 80–150 字；结合本次“减少不必要描述”的反馈，改为允许更短、信息完整的段落。UI 不展示“所见 / 可能相关 / 护理方向”三连栏目。静态定义仅藏在“了解这一项”中。

### 原话与改写

| 不采用 | 改写示例（必须有对应观察） |
|---|---|
| 混油倾向·T微光泛油 | 混合偏油。额头和鼻子的油光比两颊明显。 |
| 两颊平滑偏哑 | 两颊没有明显油光。不能因此推断干燥。 |
| 测什么·柔和光泽 | 两颊没有明显暗沉，整体气色比较均匀。 |
| 线→细纹 | 细纹。眼周和额头的细纹暂时不明显。 |
| 毛孔状态还不错 | 鼻翼两侧的毛孔比较明显。避免挤压和反复刷洗。 |
| 你现在不能用精华 | 照片里有局部泛红，先暂停新增功效精华，保留已耐受的基础护理。 |
| 缺水导致出油 | 额鼻有油光；是否干燥还需结合洗后紧绷等实际感受。 |
| 修复屏障，七天逆龄 | 删除诊断与承诺。可写“先减少摩擦和新增步骤”。 |
| 准确率 90%，把握 90% | 不生成这类字段或文案。 |
| 很乖、抢戏、开趴、玻璃肌 | 改为具体的部位与外观描述。 |

### 同一分项必须能写出差异

毛孔较好：“这张照片中，两颊毛孔不太明显。保持基础清洁即可，不需额外去角质。”

毛孔中等：“鼻翼附近能看到一些毛孔，范围比较局部。先避免挤压，清洁不必加码。”

毛孔需关注：“鼻翼两侧的毛孔比较明显。照片不能判断是否堵塞，先避免磨砂、撕拉和反复刷洗。”

看不清：“鼻翼没有拍清楚，暂时无法判断毛孔。可在均匀自然光下补拍。”

以上是写法样例，不是按分数自动填入所有人的固定文本。

## 6. 六类产品的固定评估规则

“必须评估每一类”不等于“必须购买每一类”。保湿是护理目的，乳液和面霜是两种选择，不再把“保湿”另算一瓶。

| 品类 | 本版规则 |
|---|---|
| 洁面 | 建议保留基础清洁；有油光也不要求洗到发紧，不因为毛孔分低增加洗脸次数 |
| 保湿乳/凝露 | 默认作为主要保湿；用户自述洗后发紧时改为较轻的替代选项 |
| 面霜 | 洗后发紧时建议作为主要保湿替代乳液；不发紧时不用额外加；未知时按需选择并写清条件 |
| 精华 | 近期自述刺痛发痒、泛红表现分 ≤70、希望精简或未满 18 岁时暂缓新增；无上述情形且在意干燥并自述发紧时可选保湿精华；其余不强推 |
| 防晒 | 建议保留日间防护；是否有具体候选取决于地区型号资料，不用配方猜 SPF |
| 化妆水 | 没有单独需求依据时不必加，说明已有乳液或面霜可承担保湿 |

四种状态固定为：`recommended` 建议保留、`optional` 按需选择、`not_needed` 暂时不用加、`hold` 先缓一缓。暂停的是“新增这一步/产品”，不是作出“这一类绝对不能用”的禁忌判断。

推荐产品卡至少包含：品类、名称、型号/规格/地区、2–4 个主要成分及角色、对应本次观察、3–5 句理由、使用位置、使用注意。每类最多两个候选，明确是替代关系。早晚步骤中只保留一项主要保湿，不自动把所有候选加入步骤。

本版初始目录核对了中国官网的七个型号：珂润五款、丝塔芙两款；示例展示六个候选，精华暂缓，化妆水不必加。目录是可维护的起点，不代表市场最佳排名、商业赞助或已做完预算/全成分过敏筛选。

防晒步骤仍保留，但本次没有将资料不齐的型号放进候选。珂润 30ml 的成分页与系列页信息需区分，系列页列为 SPF15；60ml 水感款虽列 SPF50+ PA++，本次未取得相应完整成分页。不能把两者配成一个推荐。丝塔芙每日舒缓防晒官网有完整成分，但本次未从同页核对到数值防护等级，且含香精，亦未匆忙纳入。用户会看到暂不列具体产品的原因。

海外目录当前为空，不能用中国版配方替代海外型号。未成年人也不自动套用成人候选。现阶段未采集预算、产品偏好、既往配方不耐受与完整在用产品，因此不宣称完成这些条件下的个性化匹配。

## 7. 图片不足与失败规则

- 七项都能判断才给总分与完整护理报告入口。
- 一至六项可判断：展示可见观察，其余为 null，肤质倾向不确定；不给总分，不出具体候选，提供“调整照片”。
- 零项可判断：说明图片不足，所有分数为空，不制造结论。
- 模型结构缺字段、诊断/承诺/百分比或部分明显矛盾：拒绝该结果，提示重新分析。
- 网络或真实模型失败：只显示失败提示。Mock 仅由显式示例入口或测试引擎触发，醒目标注“未分析你的照片”。

关键词与结构校验能拦截一部分问题，但不能证明视觉观察真实、因果完整或所有文案均无风险。上线前需要真实照片标注集、光照/肤色覆盖、人工抽检，以及模型升级回归评估。本交付未调用真实用户照片或付费模型。

## 8. UI 规范与已落地行为

暖白背景、深绿色重点、白色报告分区；减少光晕和段位装饰。结果页先给结论，分项直接给结果句。最多两个优先动作；完整报告只默认展开总览，成分及用法可在产品卡内继续展开。

报告正文 15px、行高 24–25px，标题约 21–30px，说明文字 13px；主体宽度最大 680px，手机横向留白 24px。关注状态同时有文字，不仅靠颜色。按钮和折叠项提供相应无障碍角色与状态。

保留“本次引擎”，详细模型信息折叠；示例标识始终可见。评分说明不使用百分比。已检查 320px 的输入表单与 390px 报告流程；这些是 Web 渲染检查，不能替代 iOS 真机摄像头、权限与大字号测试。

## 9. 与旧代码的关键差异

| 旧问题 | v3 行为 |
|---|---|
| 模型短评被静态“测什么”覆盖 | 直接展示本次 observation，科普定义仅作可展开说明 |
| 短标签强调画面感，出现生造词 | 普通中文完整句，内外字段名分离 |
| 缺项补默认分、随机部位、演示随机变化 | 缺项拒绝/标 null；部位来自证据；示例固定 |
| 真实引擎异常自动生成 Mock | 失败明确返回，不把示例当成真实结果 |
| 模型自由编产品与成分 | 产品目录由人核对，应用做条件选择 |
| 少数产品卡不能回答是否需要其他品类 | 六类固定评估；未推荐、暂缓、目录无匹配分别解释 |
| 缺少体感信息却推导护理 | 增加可选体感输入，未知不当作“无” |

## 10. 工程交接边界

此交接包用于继续开发与审阅。保持原有 Expo 架构，增加 Web 预览依赖。支付仍为功能预览，不会扣款；付费数据也尚未迁移到服务端鉴权。现有 Qwen 直连仅供本地开发，客户端注入 Key 的方式不适合生产发布，发布前应迁移到后端代理。海外真实引擎尚未接入。

本次未使用、复制或修改原项目的 `.env`。交接包不含 Key、node_modules、.expo、.git 或构建缓存。
